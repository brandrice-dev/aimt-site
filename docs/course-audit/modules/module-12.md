## Part III conversation-progression defect fix (August 27, 2026 — Step 93)

Owner QA of the visual/UX refactor (Step 92) surfaced a blocking functional defect in Part III, then a second, related defect on re-review. Both were fixed together; assessment content, scoring, weighting, critical-domain logic, the one-follow-up rule, thresholds, and every locked string were left untouched.

**Defect 1 — "the same question repeats" / never reaches Conversation 2/3.** Owner-reported symptom: after answering the first Cadence prompt, the flow appeared stuck and never advanced to Conversation 2, Conversation 3, Processing, or a result.

**Defect 2 — welcome text answered as if it were the primary prompt.** A follow-up owner screenshot showed the generic Part III welcome ("You made it to the final part... Ready?") rendered with an active composer beneath it; a nonsense answer to "Ready?" was then graded against a real interview's rubric and jumped straight to that interview's approved follow-up (INT-05 observed) — its primary prompt was never shown.

**Root cause (single defect, both symptoms).** `renderPartIII()` in `assets/js/module12-certification.js` fell back to the generic welcome copy whenever a conversation's `transcript` was empty — true at the start of **every** conversation (1st, 2nd, and 3rd), not only the first. The real `interviewDef.primaryPrompt` was never rendered as a chat message, and the composer was active immediately beneath the welcome text. Reproduced against the real, unmodified renderer via `scripts/review-module12-bank.mjs --browser --seed 7`: a fresh Part III attempt showed only the generic welcome (no INT-01 primary prompt visible), and a nonsense reply to "Ready?" produced INT-01's real follow-up. This fully explains both owner reports: the "repeat" was the identical generic welcome re-appearing at the start of every conversation instead of three distinct scenarios, and the specific screenshot was that same gap swallowing the primary prompt on the very first turn. Confirmed **client-controller-only** — the server (`functions/api/certification/get-part.js`, `submit-interview-turn.js`) and the local QA harness's mock endpoints already implemented the correct sequential, ID-tracked, one-follow-up state machine; nothing there needed correction beyond the parity/robustness items below.

**Fix — server-authoritative "first conversation" signal.** New pure helper `functions/_lib/certification/interview-progression.mjs` (`findNextInterview(selectedIds, conversationState)`) determines the next not-yet-finalized interview ID and whether it is the attempt's first (`conversationIndex === 0`) — conversations are always completed strictly in the fixed selection order, so this is a reliable, cheap signal without adding a separate persisted counter. `get-part.js` now uses this helper and returns `isFirstConversation` in the Part III payload; `scripts/review-module12-bank.mjs`'s mock `get-part` does the same, so the local harness and production implement the identical rule. `renderPartIII()` now only prepends the welcome + a new "Let's start with this one." line when `conversation.isFirstConversation` is true, and **every** fresh conversation (including 2nd/3rd) always renders its own real `conversation.primaryPrompt` as a message before the composer is reachable — there is no code path where a composer goes live without the actual prompt visible above it. The Review Mode fixture conversation was updated to declare `isFirstConversation: true` (a generic welcome must never carry an interview ID, and Review Mode's single fixture is always presented as "first").

**Welcome copy replaced exactly as directed.** `COPY.partIII.openingWithName`/`openingNoName` now read: "You made it to the final part, [name]. This part is a little different. I'm going to give you a few situations you might run into in practice, and I want to hear how you'd think through them. There isn't one perfect script — just talk to me the way you normally would." followed by a new `COPY.partIII.startLine`: "Let's start with this one." The old "...We're done with multiple choice... Ready?" question-and-answer framing is gone; there is no student-response turn for the welcome itself.

**Local QA harness parity fixes (unrelated latent gaps found while verifying the real state machine end-to-end).** Three issues in `scripts/review-module12-bank.mjs` — never reachable through the real renderer's normal flow, but real deviations from the production API contract — were corrected so the harness exercises the actual state machine, not a simplified stand-in: (1) its mock `submit-interview-turn` handler was missing the `if (state.finalized) return {finalized:true, alreadyFinalized:true}` short-circuit production has, so a finalized conversation could technically be resubmitted and re-scored; (2) its mock Cadence evaluator always forced the one-allowed-follow-up path on every conversation, so the immediate-finalize path was never exercised locally — it now deterministically alternates by conversation index (even = one follow-up, odd = immediate finalize), preserving the pre-existing seed-3 integration test's expectation that conversation index 0 needs a follow-up; (3) that same mock evaluator scored every rubric criterion at `1` out of a real possible `2` (the locked 0/1/2 scale in `scoring.mjs`, unmodified), which silently capped the interview component at exactly 50% — permanently below its own 80% minimum — so a genuine Mock PASS was structurally unreachable through this harness even before this task. Criterion scores now use full credit (`2`), matching the case mock's existing "solid, professional response" standard (`mockEvaluateStructuredCasePart`'s 0.75 correctness).

**New QA-only mock-outcome control.** Per the task requirement to preview both result screens without a double 40/4/3 run, the harness banner now offers "Mock PASS" / "Mock NOT YET PASSED" / "Auto" links (`/?mockOutcome=pass|not_yet_passed|auto`). Only `not_yet_passed` changes any input — it drops the mock knowledge-percent input from 0.8 to 0.5, deliberately below `config.minimums.knowledge` (0.75), so the real, unmodified `determineCertificationDecision()` (independent per-component gates, no compensation) fails on its own logic rather than a fabricated client-side decision. Clearly labeled "QA ONLY," round-trips only through this local `GET /`, never touches `/api/certification/*`, and makes zero Supabase/production writes (same guarantee the harness already had).

**Tests — 54 new deterministic assertions, zero regressions.** New `tests/certification-part3-progression.test.mjs`: pure unit tests for `findNextInterview()` (fresh/mid-attempt/all-finalized/mid-conversation-resume); static checks that `get-part.js` and `submit-interview-turn.js` implement the fix and the finalized-lock; static checks that `renderPartIII()` gates the welcome behind `isFirstConversation` and always references `primaryPrompt`; static checks for the exact approved copy and the Review Mode fixture's `isFirstConversation: true`; static checks that the client never assigns its own `decision`/`state` (cannot self-certify); and a full integration walk against the real `--browser` harness — fresh attempt reports `isFirstConversation: true` with a real (non-generic) primary prompt, refresh-before-responding returns the same interview (no premature advance), the one-follow-up and immediate-finalize paths both work, a finalized conversation cannot be restarted, all 9 harness interviews complete exactly once with no repeats, the walk reaches `allConversationsFinalized` → Processing → a real decision, and both `mockOutcome=pass`/`not_yet_passed` reach their respective decisions. All pre-existing suites remain green, including `certification-content-bank.test.mjs`'s 120/12/9 counts and 141/141 traceability, and `certification-ui-refactor.test.mjs`'s 8/8 locked-wording spot-checks (the Part III welcome string is not among those spot-checked, so the authorized copy change didn't require updating that test) — **1104 total deterministic assertions, zero regressions.**

## Review + retake flow fix (August 27, 2026 — Step 94)

Follow-up owner QA on the same session found two more issues, both pre-dating this task: **"Review My Recommended Sections" was a dead button**, and **Attempt 2 appeared to require only selected portions of the assessment rather than a fresh full 40/4/3 attempt.** Neither touched Part III (untouched and still regression-tested green), assessment wording, or scoring rules.

**Root cause 1 — dead "Review My Recommended Sections" button.** The button existed and was wired to a click handler, but that handler only ever called `window.showHome()` — a generic "go to the dashboard" navigation with no actual recommendation content. The deeper cause: `functions/api/certification/finalize-assessment.js` had always hardcoded `weakCompetencyAreas = []` when building remediation records ("grouped competency-level remediation content is authored in a later phase"), so only critical-domain remediation rows were ever created — a student who failed on ordinary competency weakness (the common case) got zero remediation rows, and the client never read or rendered `status.remediation` at all even though `get-status.js` had already been returning it since the engine was built.

**Fix.** `functions/_lib/certification/attempt-ladder.mjs` gained a new pure `collectWeakCompetencyAreas(weakSpots)` export — deduplicates already-identified weak spots (a missed Knowledge item, a below-minimum Case, a below-minimum Interview, each reduced to only a `competency` label + source module(s) + optional section ref) into one row per distinct (competency, primary module) pair, sitting right next to the pre-existing `buildRemediationAssignments()` it feeds. `finalize-assessment.js` now actually calls it: it recomputes which Knowledge items were missed from the stored responses (reusing `scoreKnowledgeResponses`'s existing `perItem` output, previously computed but discarded), which Cases scored below `config.minimums.appliedCases`, and which Interviews scored below `config.minimums.interview` (recomputed from stored `criterionScores` via the real `scoreInterviewConversation`, same "never trust a client-submitted score" principle already used for Part I) — never the item's own prompt/choices/correct answer/rationale, only its competency label and module. `assets/js/module12-certification.js` gained `renderRecommendedReview()`, reading `status.remediation` and rendering one card per area (competency/domain label, module title via real course navigation, the section reference when available, a plain-language reason, and an "Open Module N" button using the page's real `openModuleById` — no invented anchors, since the course has no sub-module section anchors to deep-link to) plus a "Back to Performance Review" button that simply re-renders `Module12Cert` (read-only, no attempt-mutating call anywhere in this view). Both "Review My Recommended Sections" (Attempt 1) and "Begin My Remediation Plan" (Attempt 2, when remediation is actually required before Attempt 3) now route to this same real view — the same underlying feature at two different ladder stages, not two separate dead ends.

**Root cause 2 — Attempt 2 appearing partial.** Production's `start-attempt.js` was already correct: it always inserts a brand-new `certification_attempts` row with a real constrained `assembleAttempt()` draw and retake-overlap minimization (`seenKnowledgeIds`/`seenCaseIds`/`seenInterviewIds` from every prior attempt) — confirmed by re-reading it start to finish. The defect was entirely in `scripts/review-module12-bank.mjs`'s local QA harness: its mock `/api/certification/start-attempt` handler unconditionally echoed back whatever `session` state already existed, including a fully finalized one, no matter how many times it was called — so re-clicking "Start Attempt 2" against the harness just showed the same already-answered Part I and the same already-submitted Part II/III state, exactly matching the owner's description. Category **A (local QA harness only)** — no production code changed for this root cause.

**Fix.** The harness now tracks cross-attempt QA state separately from the single working `session` object: `seenIds` (accumulated selected IDs across every attempt in the run), `attemptHistory` (`{attemptNumber, decision, criticalDomainResults}` per finalized attempt), and `remediationAssignments` (built via the same real `collectWeakCompetencyAreas`/`buildRemediationAssignments` helpers finalize-assessment.js now uses, not a fixture). A new `freshRealAttempt(attemptNumber)` draws a genuine, real constrained 40/4/3 (unlike the harness's original `freshSession()`, which deliberately shows *all* 12 cases/9 interviews for content-browsing convenience — that mode is unchanged and still used for the very first session) with retake-overlap minimization against `seenIds`. `/api/certification/start-attempt` now checks `session.finalized`: if not yet finalized, it behaves exactly as before (returns/resumes the current session); if finalized, it runs the real `determineNextAttemptEligibility()` ladder gate (imported, not reimplemented) and either refuses with a 409 (mirroring production's blocked-attempt response) or replaces `session` with a `freshRealAttempt()`. `/api/certification/get-status` was similarly rewired off its old hardcoded `{canStartNewAttempt:true, nextAttemptNumber:2}` shortcut onto the same real ladder function fed by `attemptHistory`/`remediationAssignments`, and now returns real `remediation` rows (filtered to the latest finalized attempt, matching production's own filtering). A small related gap found while fixing this — `get-status` kept reporting state `A` (Exam Ready) instead of `B` (in progress) immediately after a fresh `start-attempt` call, since the harness previously only inferred "in progress" from a part being locked — was also fixed with an explicit `session.started` flag, set the moment `start-attempt` returns (mirrors production inserting the row). Two new QA-only banner controls were added, clearly labeled: `?completeRemediation=1` (marks all outstanding remediation complete, so the Attempt 3 gate can be tested both blocked and unblocked without a remediation-content UI, which doesn't exist yet) and a `window.openModuleById` stub (an `alert()` confirming the correct module number, since this harness intentionally never loads the full course state machine).

**Institutional rule preserved, not changed.** Attempt 2 (and every subsequent attempt) remains a full 40 Knowledge / 4 Applied Cases / 3 Practitioner Conversations — never a "redo only what you missed" mini-retest. Non-critical-domain remediation does not block Attempt 2 (only Attempt 3+, per `config.attemptRules.remediationRequiredBeforeAttempt = 3`, unchanged) — reviewing recommended sections is study, never a gate on the very next attempt. Critical-domain remediation (unchanged, unrelated to this task) still applies from Attempt 1 onward, independently of the numbered-attempt gate.

**Tests — 51 new deterministic assertions in `tests/certification-review-retake.test.mjs`, zero regressions.** Pure unit tests for `collectWeakCompetencyAreas()` (dedup, missing-competency/missing-module skip, multi-module primary selection) and a full `collectWeakCompetencyAreas → buildRemediationAssignments → determineNextAttemptEligibility` pipeline test (outstanding remediation does not block Attempt 2, does block Attempt 3, completing it unblocks Attempt 3, Attempt 3 is never a reduced-size retest); static checks that `finalize-assessment.js` populates real weak spots and never includes prompt/choices/rationale/correctChoice in them; static checks that `renderRecommendedReview()` reads `status.remediation`, never references rubric/answer-key fields, uses real navigation, never calls `apiPost`, and that both dead buttons now route to it; and a full integration walk against the real `--browser` harness — a failed attempt produces non-empty, non-leaking remediation rows with valid module numbers, re-fetching status (simulating "open review → back") never changes attempt state, Attempt 2 gets a genuinely fresh 40-item Part I with zero carried-over responses and a real 4-case/3-interview Part II/III (not the 12/9 browse set), Attempt 2's Part III still shows a real primary prompt (Part III fix regression-checked), Attempt 3 is refused (409, `remediation_required`) until the QA-only control marks remediation complete, and Attempt 3 is then a full fresh 40/4/3 — not a smaller "missed items only" retest. All pre-existing suites remain green — **1155 total deterministic assertions, zero regressions.**

**Manual QA performed this pass.** In the real browser UI against `--browser --seed 99`: failed a full Attempt 1, clicked "Review My Recommended Sections" (real DOM click), confirmed a populated Recommended Review panel with real competency/module/section data and no answer-key leakage; clicked an "Open Module" button and confirmed it invokes `openModuleById` with the correct module number; clicked "Back to Performance Review" and confirmed the same Attempt 1 result screen re-renders unchanged; clicked "Start Attempt 2" and confirmed Part I renders "Question 1 of 40 · 0 answered" with the first question's real text, and confirmed via the live API that Part II returns exactly 4 fresh, unsubmitted cases (not 12).

## Three-part assessment engine (implemented)

### Versioned configuration
`functions/_lib/certification/assessment-config.mjs` defines `HEAD_SPA_ASSESSMENT_CONFIG` (assessment version `headspa-fe-assessment-v1`) — weights (50/30/20), independent minimums (75/75/80, overall 80), difficulty targets (20/60/20), required module coverage (1–11), Part I/II/III target counts (40/4/3), critical-domain coverage rule, and attempt-ladder rule constants. `getAssessmentConfig(version)` looks up a frozen historical config by version string so a future revision never rewrites what an earlier attempt was actually held to (standard Section 15) — add a new entry, never mutate an existing one.

`functions/_lib/certification/critical-domains.mjs` defines the four locked Head Spa domains (D1 Professional Scope/Diagnosis/Referral, D2 Contraindication/Client Safety, D3 Consent/Touch/Bodywork Authority, D4 Sanitation/Process Integrity) as versioned configuration, each with a `typeBThreshold` (2) — never as scattered one-off conditionals.

None of them ever include `correctChoice`, `rationale`, `correctAnswer`, `scoring`, `criticalFlags`, or rubric guidance.

### Constrained randomization
`functions/_lib/certification/randomization.mjs`:
- `selectPartIIAndIII()` — greedy set-cover selection of cases then interviews against the four critical domains, then fills remaining slots for module/variety coverage, preferring unseen items.
- `selectPartI()` — guarantees every required module gets ≥1 item, tops up critical-domain evidence to the required minimum (accounting for what Part II/III already covered), then fills the remaining slots targeting the ~20/60/20 difficulty mix.
- `assembleAttempt()` — orchestrates both, verifies no duplicate IDs across the whole attempt, and reports a per-domain evidence matrix + warnings.
- Explicitly returns `{ ok:false, reason:'insufficient_bank', ... }` rather than throwing when the bank can't satisfy coverage — this is the path production hits today.
- Tested against a synthetic fixture bank in `tests/certification-randomization.test.mjs` (27 assertions, all passing) — module coverage, difficulty mix, no-duplicate-IDs, domain coverage (≥2 total, ≥1 non-Part-I per domain), missing-module/too-small-bank failure handling, and retake-overlap minimization.

### Scoring + critical-domain gating
`functions/_lib/certification/scoring.mjs` implements the standard's Section 5.2 bar exactly:
- **A single missed multiple-choice question tagged as domain evidence never by itself fails a domain.** Part I evidence points are constructed with `explicitUnsafe` hardcoded `false` — that flag can only ever originate from a case/interview evaluator's structured output.
- **Type A (explicit unsafe reasoning)** — set only when a case's deterministic `criticalFlags` rule matches the student's choice, or when Cadence's structured interview/case evaluation explicitly returns it against a human-authored rubric criterion's `explicitUnsafeRule`.
- **Type B (repeated pattern)** — requires ≥`typeBThreshold` (2) independent evidence points sharing the same `patternTag`, which can originate from a knowledge item's optional `distractorPatternTags`, a case's evaluator output, or an interview's evaluator output.
- `determineCertificationDecision()` evaluates all five gates (overall, knowledge, appliedCases, interview, criticalDomains) completely independently — proven by a test where meeting every per-component minimum exactly (75/75/80) still fails because it weights out to 76% overall, and by a test where a perfect score everywhere still fails on one uncleared domain.
- Tested in `tests/certification-scoring.test.mjs` (21 assertions, all passing).

### Attempt ladder
`functions/_lib/certification/attempt-ladder.mjs`'s `determineNextAttemptEligibility()` is a pure function (no I/O) implementing standard Section 8's exact ladder — Attempt 1→2 with no extra gate, Attempt 2→3 gated on remediation completion, Attempt 3→4 gated on educator authorization, Attempt 4 unsuccessful → `individual_aimt_review` with no automatic Attempt 5, **plus** the domain-specific critical-domain remediation gate that applies starting after Attempt 1 independent of the numbered gates. `buildRemediationAssignments()` groups deficiencies by competency/critical-domain, never one row per missed question. Tested in `tests/certification-attempt-ladder.test.mjs` (12 assertions, all passing), including a case proving that remediating the *wrong* domain does not unlock the next attempt.

## Server-authoritative backend (implemented, release-blocker addressed)

Per standard Section 16, this repository's existing identity pattern (`Authorization: Bearer <supabase access token>` → `GET {SUPABASE_URL}/auth/v1/user` with the service-role key → entitlement check against `course_entitlements`) is reused exactly, factored into `functions/_lib/certification/auth.mjs`. No parallel auth system was introduced.

### Schema (additive) — `supabase/migrations/20260826_create_certification_assessment.sql`
- `certification_attempts` — one row per attempt: versioning columns (`assessment_version`, `standard_version`, `bank_version`), per-part selected IDs/responses/state, component scores, `critical_domain_results`, `certification_decision`, `decision_at`.
- `certification_remediation_assignments` — grouped by competency/domain.
- `certification_educator_requests` — MVP manual-scheduling record; an educator authorizes Attempt 4 by setting `attempt4_authorized` directly (out of band, not via a student-facing endpoint).
- `certification_review_requests` — human review/appeal MVP.

All four tables: RLS `select` policy restricted to `user_id = auth.uid()`, **no insert/update policy for `authenticated`/`anon`** — matching the existing `completions` table's trust model exactly. Every write goes through the service-role key inside `functions/api/certification/*.js`. A student cannot alter their own score, critical-domain result, or certification decision by writing to Supabase directly.

**This migration is committed for record-keeping only — it has not been run.** Per `CLAUDE.md`, it must be executed manually in the Supabase SQL editor before any of the endpoints below can function.

### Endpoints — `functions/api/certification/*.js`
`start-attempt` (resolve identity/entitlement/eligibility, enforce the ladder, assemble + persist a new attempt) · `get-part` (fetch Part II/III client-safe content for an active attempt) · `save-progress` (Part I/II autosave, locked-part writes silently ignored) · `submit-part1` (server-side knowledge scoring, locks) · `submit-case` (deterministic + Cadence-evaluated case scoring, locks a case, locks Part II once all cases are in) · `submit-interview-turn` (Cadence conversation turn, max one follow-up, locks a conversation, locks Part III once all conversations are in) · `finalize-assessment` (weighted overall + critical-domain gating + certification decision + remediation-assignment generation, idempotent) · `get-status` (the single source of truth `Module12Cert.render()` reads) · `request-educator-remediation` · `request-review`.

`functions/_lib/certification/cadence-grader.mjs` calls the Anthropic Messages API directly (fetch only, its own `ANTHROPIC_API_KEY` env var) rather than routing through the client-facing `headspa-proxy` Worker — rubrics and scoring logic must never reach the browser, and the Worker's contract is designed for client-issued, client-visible checkpoint prompts. Evaluator failures preserve the student's submitted response and return a retriable error rather than silently locking, losing the answer, or falsely scoring (task requirement #40).

### Certificate issuance hardened (release-blocker)
`functions/api/issue-certificate.js` gained one additional check (Step 4b, between the existing progress-score gate and issuance): a `certification_attempts` row with `certification_decision = 'pass'` must exist for the student/course, or issuance is refused with `409`. This is **in addition to**, not instead of, the existing modules-0–11 progress gate. Because the production content bank is empty, this check can never currently pass — certificate issuance is correctly, verifiably blocked until real exam content ships and a real student passes.
